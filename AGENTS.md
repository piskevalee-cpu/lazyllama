# LazyLlama

Bun/TypeScript OpenTUI TUI that manages one `llama-server` child process and chats over its OpenAI-compatible REST API.

## Toolchain and commands

- Use Bun; `.mise.toml` pins Bun `1.4.2`. Do not replace it with Node when running the app or OpenTUI code.
- `bun run dev` | `bun run typecheck` | `bun run build` | `bun test ./test/*.test.ts`
- `bun run setup` is the setup wizard (hardware, backend, models dir, PATH). It is explicit-only, like `install:server`. The script is named `setup`, never `install`: package managers run an `install` script as a lifecycle hook, so a plain `bun install` would start provisioning.
- Focus one suite with `bun test test/core.test.ts` or `bun test test/opentui-config.test.ts`; keep tests scoped to `./test/*.test.ts` because broader filters also discover nested dependency tests.
- Provisioning is explicit-only, and lives in two entries: `bun run setup` is the TUI wizard in `src/install.ts` (it also writes `settings.json` and the `~/.local/bin/lazyllama` shim, and only touches a shell rc after an explicit confirm), and `bun run install:server` is the non-interactive server-only path. Neither ever runs implicitly, and the app itself never provisions, compiles or edits `PATH`.
- No lint, formatter or codegen configuration currently exists; do not invent commands for them. `README.md` follows the Best-README-Template structure and deliberately has **no ASCII art**; the wordmark in `src/logo.ts` is for the splash only.

## Release

- UI and feature work lands on `beta` and is pushed to `origin/beta`; `main` is not the working branch. CI runs on a push to `beta` (typecheck -> build -> `bun test ./test/*.test.ts`), so push after the local suite is green and watch the run if the change touches the renderer.

## Architecture

- `src/index.ts` is the app entrypoint: CLI parsing, boot flow, server startup, and chat wiring. `src/ui/` owns the OpenTUI renderer and screen state: `controller.ts` is the session state machine and keymap owner, `chatView.ts` composes `transcript.ts` + `prompt.ts` + `sidebar.ts`, `shell.ts` is the root chrome, and `splashView.ts`/`hubView.ts` own the pre-chat screens. `layout.ts`, `keys.ts`, and `bindings.ts` hold pure breakpoint/keymap/command logic with no OpenTUI imports.
- `src/backends.ts` is the single source of truth for the backend catalog (`BACKEND_CATALOG`: asset tokens, platforms, arches, size, device tokens, driver minimum, fallbacks); the wizard, the downloader, the verifier and the README backends table all read it. `proposeBackend` picks the CUDA slice by driver major, and asset picking is arch-aware. `src/paths.ts` owns XDG roots, the shim, `PATH`/rc handling and the app copy's dependency closure; `src/settings.ts` owns `settings.json` (`LAZYLLAMA_MODELS_DIR` still wins over it).
- `src/config.ts` contains pure launch-config logic and `CONFIG_FIELDS` (tunable launch options are data-driven); `src/server.ts` owns the child process, readiness polling, and REST/SSE helpers; `src/installer.ts` owns provisioning; `src/models.ts` scans `models/`.
- **Off-by-default, and the vocabulary is not invented here.** Every tunable outside the context group is `null`, and `null` means the flag is not in the command at all, so llama.cpp's documented default applies; the editor prints `default (<defaultNote>)` rather than a bare `off`. Only `-c` is always sent, because `-c 0` is llama.cpp's own "use the model's context". Each `defaultNote`, and every `autoValue`, is copied from the vendored `llama.cpp/` (see `tools/server/README.md` and `common/arg.cpp`) — when llama.cpp changes a default, the field data and `src/manual.ts` change together, and `test/core.test.ts` fails until they do.
- `CONFIG_FIELDS` field mechanics: `optional` marks a droppable value; `defaultNote` is what the omission resolves to; `autoValue` is a state llama.cpp itself spells (only `-ngl` and `reasoning_format` have one, and a test asserts it is reachable in `fieldStates`); `onValue` names the number a numeric field switches on to (a function for `-t`/`-tb`, which follow hardware concurrency). Numbers cycle `default -> onValue -> ... -> max -> default`; optional booleans walk a three-state ring `default -> --flag -> --no-flag`; optional text walks `fieldStates(def)`, whose first element is the default state, so a value is always droppable by walking one full ring. `configValue(key, value)` renders a raw value exactly as the editor does, so the side panel and the in-chat overlay never disagree with the editor.
- Thinking is two independent request parameters, not one: `thinking` is `reasoning_effort` (whether the model reasons, and how hard) and `reasoning` is `reasoning_format` (how the reasoning text comes back). Both default to absent. The transcript's thought block is built from `reasoning_content` **streaming deltas**, so `deepseek-legacy` leaves the block empty and leaves `<think>` tags in the answer; `none` leaves the thinking inline. The server-level `--reasoning`, `--reasoning-budget` and `--reasoning-preserve` are not exposed as fields and stay reachable through `extra`.
- `--props` is not needed for the app: `GET /props` is read-only without it and still returns `default_generation_settings.n_ctx`, which is all `readNCtx` reads. Only `POST /props` needs the flag, so `enableProps` is a normal droppable field. `--metrics` is read by nothing here.
- Boot flow is splash -> model picker -> config editor -> `[ Confirm & start ]` -> chat. `--model` skips the picker and opens the editor. Empty or multiple local models are not silently auto-selected by the current code.
- Chat requests must snapshot completed history before `startAssistant()` appends its placeholder; never send the live transcript array. Empty assistant placeholders are filtered from requests. Requests pin `id_slot: 0` with `cache_prompt` and `stream_options.include_usage`; context used is `timings.cache_n + prompt_n + predicted_n` and tok/s is `timings.predicted_per_second`. Read the limit with `readNCtx` (`/props` nests it under `default_generation_settings`). Requests carry `reasoning_format` (`auto` splits model thinking into `reasoning_content` deltas, `none` keeps it inline) and the prompt is an L-shaped `Box` (left `┃` rule, `╹` corner, `▀` bottom rule) that grows from 1 to `max(6, height/3)` rows.
- `ServerManager` owns one subprocess. Binary resolution is `LAZYLLAMA_SERVER_BIN` -> installer receipt -> installer directory -> local `llama.cpp/build/bin/llama-server`; otherwise the user must run `bun run setup` (or `bun run install:server` for the server only). Startup refuses to claim readiness when another healthy server is already on that host/port, and it verifies that the newly spawned child is still alive after readiness. Ctrl+C, SIGINT, SIGTERM, and SIGHUP share one idempotent shutdown path (`src/shutdown.ts`) that stops the managed server before destroying the renderer. Chat requests pin `id_slot: 0` with `cache_prompt` and `n_keep` so llama.cpp reuses conversation KV cache across turns.
- `llama.cpp/` is git-ignored reference/build source: never edit or commit it. Model blobs in `models/` are git-ignored; `models/README.md` is committed.
- `src/manual.ts` is the parameter manual's copy: pure data, no TUI import, every default and accepted value taken from the vendored `llama.cpp`, and `fieldKey` linking an entry to its `CONFIG_FIELDS` row so the screen can show the value in force. `src/ui/manualView.ts` only renders it (one `TextRenderable` per line, built once, values refreshed on open — never rebuilt on every open). `?` and `F1` open it from any screen and `Esc` returns to the exact screen *and row*, via `manualReturn` + `manualFocusId` and `HubView.focusById`. `?` is claimed only after `hub.isEditing()`, so it still types inside the inline editor.
- The manual's scrolling is driven by the controller (`MANUAL_SCROLL_KEYS` -> `ManualView.scroll`), **not** by the focused `ScrollBoxRenderable`: the controller's `keypress` listener runs first and would swallow the keys. The controller's key branches must also stop every other key on that screen, or a stray Enter reaches the chat keymap behind it.
- Branding lives only in `src/logo.ts`; splash animation stays pure in `src/splash.ts` and width-aware for the block wordmark. The splash's loading line is an indeterminate `sweepFill` meter from `src/ui/meter.ts`, the same gradient the side panel uses, and the status label is never duplicated. `src/ui/theme.ts` is monochrome: black and white over a grey ramp (`background #000000`, `panel #0a0a0a`, `element #141414`, `border #262626`, `muted #8c8c8c`, `text`/`accent` `#ffffff`). `meter` is a three-step white-to-grey ramp and `meterTrack` the dim track, and `SidebarRow.bar` rows paint a fill that fades through that ramp instead of a flat block. Element surfaces use `theme.element`; message bubbles use `theme.panel`. The chat view is OpenCode-shaped: no header bar and no bottom status bar, only the transcript, the prompt dock, and the side panel. A screen's *title* is a header row of its own (`hub-title-row` is a padded box wrapping `hub-title`, `manual-header` likewise), never a bare text node pressed against the content below it. `shell.footer` stays the only chrome: the key reference on the left and `<model> · <source> · <status>` on the right, with `hintsFor()` shortening the reference so the two never overlap. Model names come from `modelDisplayName`; full paths are abbreviated only in details.
- The side panel replaces both the old footer context readout and the fixed perf column: 42 columns wide, a flex column above 120 columns, an absolute overlay with a scrim below it, toggled with `ctrl+b`, and its preference persists in `configDir()/ui-flags.json` (`LAZYLLAMA_CONFIG_DIR` overrides that path, which is how tests stay hermetic). Context, model, server, GPU and system sections each fold with `▸`/`▾`. A section with no rows is hidden entirely (the GPU section on a machine with no GPU), and the `alt+b` cursor only walks visible sections.
- `src/vram.ts` owns dedicated GPU memory: `nvidia-smi` first, then the DRM sysfs `mem_info_vram_{total,used}` counters that amdgpu and i915 publish (hex bytes), then `rocm-smi`, then Apple unified memory marked `shared`. Detection picks the first source that answers and keeps it, because each probe is a process spawn and this runs on the panel's one-second tick. Shared-memory parts report `shared` and no meter rather than inventing a number, and an unknown counter shows `--` instead of a zero-length bar. `gibValue`/`formatGiB` in `src/ascii.ts` are the only GiB formatters, and they treat 0 as a real reading: an idle card uses no VRAM. Panel rows are laid out per kind: plain rows get the full remainder after the 13-column label so a number is never cut, and only meter rows reserve space for the percentage and bar. Context reads `context size`, `used` and a gradient meter; Model has no `ctx` row (it belongs to Context); System uses the same meters and lists every core with its percentage. `readSlotContext` (`perf.ts`) turns a `/slots` payload into a live prompt+generated footprint, so the meter moves while the model is still working. It belongs to the chat surface only: `ChatScreen.hide()` clears the panel-active flag so the splash, model picker, and config editor own the full terminal width without touching the stored preference.
- The in-transcript `⠋ thinking` placeholder and the thought block are mutually exclusive: the placeholder disappears on the first reasoning delta, the header then carries OpenCode's Braille spinner (`⠋ thinking…` at 80ms) while the model reasons, and it becomes `▾ Thought for {duration}` only once the first content token lands. The prompt box has no animation: its left footer slot is the model name, permanently. Every message box always gets a blank row above it, so a reply never touches the previous message.
- Stopping generation closes the request: the two-step Esc (`session.interrupt`) aborts the in-flight `fetch`, and llama-server cancels the task and frees the slot when the client disconnects. There is no `/stop` endpoint to call. Interrupted answers keep their partial text and get a muted `· interrupted` suffix.

## OpenTUI/input rules

- Load the `opentui` skill for UI work. The UI is imperative `@opentui/core`; do not switch to React/Solid or another renderer unless explicitly requested.
- Mouse reporting is on by default for OpenCode parity (wheel scroll, click-to-focus, hover, copy-on-release via `copyToClipboardOSC52`, `ctrl+y`); `--no-mouse` or `LAZYLLAMA_NO_MOUSE=1` turns it off. Keyboard remains the primary interface.
- The chat prompt is a `TextareaRenderable`: plain Enter is claimed by the global keymap (`key.preventDefault()`) and committed by the orchestrator, while shift/ctrl/alt+Enter and `ctrl+j` are registered as `newline` bindings on the textarea. Do not rely on `onSubmit` from `InputRenderable`; in OpenTUI 0.5.12 it is not invoked by `InputRenderable.submit()`. Hub one-line inputs still use `InputRenderableEvents.ENTER`.
- Hub selection uses native `SelectRenderable` focus, navigation, and `ITEM_SELECTED` events. Selection indicators are disabled in favor of a custom `▸` marker. Global `KeyEvent.name` is canonical `"return"`; compatibility bindings also cover `"enter"`, `"kpenter"`, and `"linefeed"`.
- When editing an inline input, let non-Escape keys reach the focused renderable. Use `@opentui/core/testing` (`createTestRenderer`, `mockInput.pressEnter()`) for keyboard/focus tests, and always destroy the test renderer in cleanup.
- Every vertical scroller (hub editor, transcript, side panel) keeps its scrollbar on the right edge and passes `verticalScrollbarOptions` in the `ScrollBoxRenderable` **constructor**, which leaves the bar's manual-visibility flag unset so it auto-hides whenever the content fits. Assigning the same options through the property setter sets that flag and pins the bar permanently — do not do that unless a surface really wants an always-on bar.
- The chat column keeps a one-row `gap` above the prompt dock so the last message never touches the prompt, and the prompt panel is a raised `element` surface rather than the message `panel` colour.
- The chat layout math lives in `layout.ts` (`isWide` >120, `SIDEBAR_WIDTH` 42, `sidebarMode`, `promptMaxHeight`, `scrollDelta` where a "page" is half the viewport and a "half page" a quarter). The transcript is a sticky-bottom `ScrollBoxRenderable`; streaming markdown is throttled to ~30fps and flushed on completion, and finalization is asynchronous, so UI tests must sleep briefly before asserting on rendered markdown.
- Chat surfaces are frameless OpenCode-style `Box`es (panel background, single left rule, no full outer frames). The user message is the only one with a panel and accent rule; assistant turns are plain text indented 3 columns so they line up with the text inside the user's bubble, with no model-name prefix, a muted `▣ {tokens} tok · {tok/s} tok/s · thought {duration}` footer, and a collapsible `▾ Thought for {duration}` line plus body driven by `reasoning_content` deltas (`ctrl+t` toggles thinking globally). Never nest a rule inside a message: a second left rule drew a stray bar beside the header and footer. Progress uses `█`/`░` blocks and Braille activity frames through `Text` renderables, never custom ASCII frames. The splash shows only the logo (reveal + ping-pong glint, no hint text). Streaming and perf polling must not block the renderer/input loop.
- OpenTUI 0.5.12 traps to avoid: never pass `wrapMode` to a `TextRenderable`/`staticText` constructor (it measures to width 0 and paints nothing) — set it after construction; never set `flexDirection` on a `ScrollBoxRenderable` (it stacks the scrollbar under the content and steals rows); `Yoga` defaults `flexShrink` to 0, so a flex child that must yield space to a fixed-width sibling needs `flexShrink: 1` and `minWidth: 0`; setting `focusedBorderColor` at runtime calls `initializeBorder()` and turns a frameless box into a 3-row bordered one.

## Tests and scope

- `test/core.test.ts` covers pure config/model/ASCII parsing. `test/backends.test.ts` covers the catalog, availability and arch/driver-aware asset picking. `test/setup.test.ts` covers `settings.json`, the models-directory precedence, the shim, PATH/rc handling and the dependency closure. `test/installer.test.ts` covers the receipt and binary discovery. `test/install-ui.test.ts` walks every wizard screen. None of them touch the network, a GPU or a real TTY. `test/server.test.ts` covers startup guards without spawning a real server.
  `test/ui.test.ts` covers OpenTUI keyboard/focus/mouse behavior with `@opentui/core/testing` rather than a real TTY, and points `LAZYLLAMA_CONFIG_DIR` at a fresh temp dir per test so UI toggles never touch the user's real flags or leak into the next test. `test/layout.test.ts` and `test/keys.test.ts` cover the pure breakpoint and keymap layers, including the Escape precedence chain (modal -> selection -> interrupt -> clear prompt).
- `@opentui/core/testing`'s `mockInput.pressKey` takes literal characters or `KeyCodes` escape sequences, never key *names*: `pressKey("pagedown")` types the letters p-a-g-e-d-o-w-n and produces no scroll, which is why page/home/end assertions use `\u001B[6~`, `\u001B[F` and `\u001B[H`. `test/core.test.ts` also carries the `CONFIG_FIELDS` invariants (every optional field has a `defaultNote`, every `autoValue` is reachable in `fieldStates`) and the manual's coverage, so a field cannot be documented in one place and missing from the other.
- Config UI fields are data-driven through `CONFIG_FIELDS`; add new launch tunables there so hub rendering and editing stay in sync. Each field also needs a `CONFIG_GROUP_ORDER` group. The editor is one vertical column: plain arrows walk every field and action top to bottom (Shift+arrows keep native fast scroll); Tab/Shift+Tab jumps between groups and actions. Its `ScrollBoxRenderable` must stay a flex-grown row with group spacing on `contentOptions`, and the density budget is `terminalHeight - 1` because only the chrome row sits outside the editor body. Editor actions are keyboard-focusable boxes, not a flat list. Lateral arrows are context-sensitive (adjust focused values, move between Back/Save/Confirm on actions, move model selection, adjust the in-chat overlay); footer hints must match actual handling. The editor uses comfortable spacing when tall and compact density when short (`requiredEditorRows`/`selectEditorDensity`); scrolling remains only for terminals too short for compact. `requiredEditorRows`'s `chrome` constant counts every row inside the editor body above the field groups (title, the blank row under it, the action row, the status line): add a row to the editor and that constant has to move with it, or comfortable density quietly overflows.
